# خطة تقييد صلاحيات مشرف الحجوزات — Golden Touch

**الهدف:** عمل المشرف (`staff`) محصور في **إدارة الحجوزات الحالية والقادمة**: حجز، تعديل موعد، إلغاء، وإدارة بيانات الزبون الأساسية. لا يرى أي سعر أو مبلغ أو إحصائية، ولا أي حجز سابق.

**المنفّذ:** Claude Code. **طريقة العمل:** 6 مراحل. نفّذ مرحلة واحدة كاملة، شغّل الفحص، حدّث «سجل التقدّم» أسفل الملف، **ثم توقّف** وانتظر الأمر بالبدء بالتالية. لا `git add/commit/push`. قواعد `CLAUDE.md` سارية (RTL، الألوان الدلالية، الحركة، التباين، رسائل عربية).

---

## 1. المبدأ الحاكم

**الخادم هو المصدر الوحيد للحقيقة.** إخفاء العنصر في الواجهة تجميل فقط؛ المشرف قادر على استدعاء الـ API مباشرة. لذلك:

1. الحقول المالية **لا تُرسَل أصلاً** في استجابات المشرف (لا `price` ولا `paidAmount` ولا `revenue`…)، لا تُخفى في الواجهة فقط.
2. الحجوزات السابقة **لا تُرجَع** من أي مسار (`/bookings`، `/bookings/day`، `/bookings/:id`، `/customers/:id`) مهما كانت معاملات الطلب.
3. الواجهة تتبع الصلاحية نفسها (`can(...)`) وتحذف العناصر بدل تعطيلها، وتعيد توزيع المساحة (قاعدة الكثافة في CLAUDE.md العام).

## 2. القرارات المحسومة (لا تُعاد فتحها دون طلب المستخدم)

| #   | القرار                                                                                                                                                                       | السبب                                                                                   |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| D1  | **«سابق» = أي حجز يبدأ قبل بداية اليوم الحالي** بتوقيت الصالون. المشرف يرى اليوم والقادم فقط.                                                                                | جدول اليوم يحتاج كل حجوزات اليوم (حتى ما مضى من ساعاته) ليعمل منع التداخل والفراغات.    |
| D2  | صلاحيتان جديدتان للمدير فقط: **`finance.read`** (الأسعار والمبالغ) و**`bookings.history`** (الحجوزات السابقة وسجل الزبون).                                                   | فصل المال عن السجل؛ كل منهما يُمنح مستقلاً لاحقاً (مثلاً مشرف أول يرى السجل دون المال). |
| D3  | يُسحب من المشرف `stats.read` فقط. **يملك `bookings.complete`**: «تأكيد الحجز» = إكماله دون أن يُدخل مبلغاً أو يراه.                                                          | الإحصائيات مالية؛ أما الإكمال فعمل تشغيلي يومي يحتاجه المشرف (تعديل المستخدم).          |
| D4  | شريط «حجوزات منتهية تحتاج إغلاقاً» (`/bookings/overdue`) يبقى للمشرف **ضمن نافذته (اليوم) فقط**؛ المدير يرى منتهيات كل الأيام.                                               | يحتاج المشرف إغلاق حجوزات اليوم؛ ما قبله سجل سابق.                                      |
| D5  | المشرف يبقى بـ `services.read` لقراءة **الاسم والمدة فقط** (يحتاجهما نموذج الحجز). الـ API يحذف `price` عنه، وصفحة «الخدمات والأسعار» تتطلب `services.update` فتختفي عنه.    | لا يرى الأسعار ولا يعدّل الخدمات، ويبقى الحجز ممكناً.                                   |
| D6  | المشرف لا يحدّد سعراً ولا مبلغاً: يرفض الـ API `price` و`paidAmount` منه (403). السعر يُحسب تلقائياً (D11).                                                                  | السجل المالي يبقى سليماً.                                                               |
| D7  | يستطيع المشرف إعادة فتح حجز **ملغى** أو **مكتمل** ضمن نافذته (لتصحيح خطئه). إن كان المدير قد عدّل المبلغ المدفوع (≠ سعر الحجز) يُرفض بـ 403 «راجع المدير» فلا يضيع تصحيحه.   | تصحيح خطأ إلغاء شائع دون المساس بالمال.                                                 |
| D8  | ملف الزبون للمشرف: الاسم والهاتف والملاحظات + **الحجوزات القادمة فقط**؛ لا زيارات ولا آخر زيارة ولا مجموع مدفوع ولا عدد ملغاة.                                               | هذه كلها مشتقة من الماضي أو من المال.                                                   |
| D9  | الصلاحيات تُقرأ من القاعدة في كل طلب (`validateUser`) فلا جلسات قديمة معلّقة بصلاحيات سابقة.                                                                                 | لا حاجة لتسجيل خروج جماعي.                                                              |
| D10 | **الإنتاج يحتاج migration بيانات:** `render.yaml` يشغّل `db:migrate` ولا يشغّل `db:seed`، فالصلاحيات الجديدة لن تصل إلا بـ migration. الـ seed يبقى للتطوير وإعادة المزامنة. | تجنّب حالة يكون فيها الكود جديداً والصلاحيات قديمة.                                     |

**D11 — احتساب المبلغ عند تأكيد المشرف** (قرار المستخدم):

1. المبلغ المدفوع المسجَّل = **سعر الحجز المحفوظ** (`booking.price`)، وهو إمّا سعر الخدمة الافتراضي وقت الحجز، أو **السعر الذي حدّده المدير** إن حجز بنفسه وحدّد سعراً.
2. إن كان `booking.price = 0` (يعني «غير محدد» في النظام كله) واستُعمل سعر الخدمة الحالي إن كان > 0، ويُحفظ على الحجز. هذا يغطي حجزاً أُنشئ قبل أن يحدّد المدير سعر الخدمة.
3. المدير يبقى قادراً على إدخال مبلغ مختلف عند الإكمال، وعلى «تعديل المبلغ» لاحقاً.
4. تغيير المشرف لـ**خدمة** الحجز يُعيد السعر إلى سعر الخدمة الجديدة (سلوك قائم)؛ تغيير الوقت أو المدة أو الملاحظات يُبقي السعر كما حدّده المدير.

## 3. نتيجة التحليل — أين يتسرّب المال والسجل اليوم

## 4. المراحل

### المرحلة 1 — نموذج الصلاحيات (الأساس)

- ملف مشترك `apps/api/prisma/permissions.ts` فيه `PERMISSIONS` و`STAFF_PERMISSIONS` (يستورده الـ seed والاختبار).
- صلاحيتان جديدتان: `finance.read`، `bookings.history` (للمدير تلقائياً).
- سحب `stats.read` من المشرف (يحتفظ بـ `bookings.complete` — D3).
- Migration بيانات idempotent (`ON CONFLICT`) تضيف الصلاحيتين وتربطهما بالمدير وتفصل صلاحية الإحصائيات عن المشرف.
- اختبار «مصفوفة الصلاحيات»: يثبّت ما يملكه المشرف وما لا يملكه حرفياً، ويفشل إن أُضيفت صلاحية محظورة له.
- **القبول:** `lint`/`typecheck`/`test` للـ API ينجحون؛ لا تغيير سلوكي بعد (لا يُطبَّق على قاعدة حقيقية في هذه المرحلة).

### المرحلة 2 — الـ API: الحجوزات

- ملف نقي `booking.visibility.ts`: `canSeeFinance`/`canSeeHistory`، `historyCutoff(now, timezone)`، `toBookingView(booking, caps)` (يحذف المال)، `toDaySummary`.
- `BookingsService` يستقبل `AuthUser`: حذف المال، فرض نافذة D1 في `day/findAll/findOne/update/cancel/reopen`، رفض `price`/`paidAmount` (D6)، قيد إعادة الفتح (D7).
- `complete`: `CompleteBookingDto.paidAmount` يصبح **اختيارياً**؛ دالة نقية `resolvePaidAmount(booking, servicePrice, dtoAmount, caps)` تطبّق D11 (مع رفض المبلغ الصريح من المشرف).
- `overdue`: يُقيَّد بنافذة المشرف (اليوم) ويُحذف منه المال؛ المدير يرى الكل.
- اختبارات وحدة للملف النقي (حدود منتصف الليل بتوقيت الصالون، تواريخ سابقة، حقول محذوفة).
- **القبول:** مشرف يطلب `/bookings/day?date=<أمس>` → 403؛ `/bookings/:id` لحجز سابق → 404؛ لا `price` في أي استجابة له؛ `POST /bookings/:id/complete` منه بلا جسم → 200 ويُسجَّل `paidAmount = سعر الحجز` (والمدير يرى القيمة)، وبجسم `paidAmount` → 403؛ حجز أنشأه المدير بسعر مخصص يُسجَّل بسعره المخصص.

### المرحلة 3 — الـ API: الزبائن والخدمات

- `customers.findOne`: للمشرف بيانات أساسية + القادمة فقط بلا مال (D8). `findAll`: بلا `visits`/`lastVisitAt`.
- `services`: حذف `price` للمشرف في `findAll/findOne`.
- التحقق من أن `stats` و`users` و`roles` تعيد 403 للمشرف.
- **القبول:** لا مسار يعيد مالاً أو ماضياً للمشرف؛ اختبارات وحدة لدوال التحويل.

### المرحلة 4 — الواجهة: الأساس والتنقل

- `types/api.ts`: جعل الحقول المالية اختيارية وإضافة أنواع ملف الزبون المقيّد.
- `can('finance.read')` و`can('bookings.history')` بدل `isAdmin` حيث ينطبق.
- القوائم والمسارات: الخدمات تتطلب `services.update`؛ الإحصائيات (موجودة بـ `stats.read`)؛ التحقق من `BottomNav`/`AppSidebar`/`more` أنها تعيد توزيع المساحة بعد الحذف.
- **القبول:** المشرف لا يرى زر الإحصائيات ولا الخدمات؛ فتح `/stats` أو `/services` يحوّله بإشعار.

### المرحلة 5 — الواجهة: شاشات الحجز

- حذف المال من `BookingCard`، `BookingSheet` (السعر/المدفوع/تعديل المبلغ؛ وللمشرف زر «تأكيد الحجز» بخطوة تأكيد واحدة بلا نموذج دفع ولا ذكر مبلغ في الإشعار)، `BookingForm` (حقل السعر وشريط المجموع ← شريط ملخص بلا سعر)، `ServicePicker`، وبطاقة «الدخل» (الشبكة تصبح 3 أعمدة).
- حجب الماضي: `DateStrip` لا يرجع قبل اليوم، تبويبا «السابقة/فترة» في `bookings/index.vue` للمدير فقط (ومع بقاء «القادمة» وحدها يُحذف المبدّل)، `OverdueBanner` يبقى للمشرف (حجوزات اليوم فقط، بلا مبالغ)، ملف الزبون (D8) وقائمة الزبائن.
- بلا تعليقات HTML بين فروع `Transition`؛ تباين ≥ 4.5:1 وحجم ≥ 13px فيما يُعاد ترتيبه.
- **القبول:** مسح بصري كامل بحساب مشرف على الموبايل والمكتب؛ لا ثقوب فارغة في التخطيط.

### المرحلة 6 — الاختبار الشامل والتوثيق والتطبيق

- اختبار e2e بحساب مشرف: مصفوفة 200/403/404 لكل مسار، وغياب الحقول المالية.
- تحديث `README.md` (جدول الأدوار) و`CLAUDE.md` (قاعدة: أي حقل مالي/تاريخي جديد يُحجب عبر `booking.visibility`)، وتنبيه في `WHATSAPP_REMINDERS_PLAN.md` بأن رسائل التذكير لا تتضمن السعر.
- `npm run lint && npm run typecheck && npm test && npm run build`.
- تطبيق الـ migration على Supabase (بعد استعادة صحة المشروع) وتحقق فعلي بتسجيل دخول `staff@goldentouch.local` واستدعاء المسارات.
