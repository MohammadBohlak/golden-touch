# خطة الحجوزات الدورية — Golden Touch

**الهدف:** زبون له موعد متكرر يُحجز له تلقائياً دون إعادة إدخاله كل مرة. الحالات المطلوبة:

1. **أسبوع نعم وأسبوع لا** — كل سبت الساعة كذا.
2. **كل أسبوع** — يوم كذا الساعة كذا.
3. **كل أسبوع بخدمة متناوبة** — مرة الخدمة (أ) ومرة (ب).

**المنفّذ:** Claude Code. **طريقة العمل:** 8 مراحل. نفّذ مرحلة واحدة كاملة، شغّل الفحص، حدّث «سجل التقدّم» أسفل الملف، **ثم توقّف** وانتظر الأمر بالبدء بالتالية. لا `git add/commit/push`. قواعد `CLAUDE.md` سارية (RTL، الألوان الدلالية، الحركة، التباين، رسائل عربية) وكذلك قاعدة الإنتاج أدناه.

> **قاعدة الإنتاج (ذاكرة المشروع):** قاعدة Supabase في `apps/api/.env` هي **الإنتاج الحي**، وهي القاعدة الوحيدة. لا `db:seed`، لا `migrate dev`/`migrate reset`، لا `app.e2e-spec.ts`، ولا أي كتابة فعلية إلا بموافقة صريحة (لقطة + معاملة بتحقق + تراجع). كل اختبارات الكتابة بـ Prisma وهمي. التفاصيل في §6.

## 2. القرارات المحسومة (لا تُعاد فتحها دون طلب المستخدم)

| #   | القرار                                                                                                                                                                                                                                                                                                    | السبب                                                                                  |

| D1  | **حجوزات حقيقية مولَّدة مسبقاً** ضمن أفق متحرّك **56 يوماً** (يُضبط بـ `RECURRING_HORIZON_DAYS`). السلسلة (قالب) + حجوزات عادية مرتبطة بها.                                                                                                                                                               | أقل تعديلاً على الكود الحالي، ويرى الاستقبال المواعيد القادمة محجوزة فلا يعطيها لغيره. |
| D2  | التكرار = **كل N أسبوع** (N من 1 إلى 4) في يوم أسبوع **أول موعد** (`startDate`). لا تكرار شهري في هذه الخطة. «أسبوع نعم وأسبوع لا» = N = 2 وطوره يحدّده `startDate`.                                                                                                                                      | يغطي الحالات الثلاث؛ الطور صريح لا تخميني.                                             |

| D5  | **لا يُنشأ موعد** إن: `startAt ≤ الآن`، أو يوم عطلة، أو خارج ساعات الدوام (بداية أو نهاية)، أو خدمته مؤرشفة/معطّلة، أو يتداخل مع حجز قائم. هذه **«مشكلات» تُعرَض ولا تُفشل العملية** ولا تزيح حجزاً.                                                                                                      | زبون ثابت يفقد موعده بصمت أسوأ من إشعار واضح.                                          |

## 3. النموذج

### قاعدة البيانات (additive — لا حذف ولا تغيير لأعمدة موجودة)

```prisma
model RecurringBooking {                       // @@map("recurring_bookings")
  id            String    @id @default(uuid()) @db.Uuid
  customerId    String    @db.Uuid               // Customer — onDelete: Restrict
  startTime     String                           // "HH:mm" بتوقيت الصالون
  startDate     DateTime  @db.Date               // أول موعد: يحدّد يوم الأسبوع والطور
  intervalWeeks Int       @default(1)            // 1..4
  endDate       DateTime? @db.Date               // آخر يوم (شامل) — null = مفتوح
  notes         String?
  stoppedAt     DateTime? @db.Timestamptz(3)
  createdById   String?   @db.Uuid               // User — onDelete: SetNull
  createdAt / updatedAt
  services      RecurringBookingService[]
  bookings      Booking[]
  @@index([customerId])
}

model RecurringBookingService {                // @@map("recurring_booking_services")
  recurringId String @db.Uuid                    // onDelete: Cascade
  position    Int                                // 0-based
  serviceId   String @db.Uuid                    // Service — onDelete: Restrict
  @@id([recurringId, position])
  @@index([serviceId])
}

// Booking +=
//   recurringId     String? @db.Uuid            // onDelete: SetNull
//   occurrenceDate  DateTime? @db.Date          // التاريخ المخطَّط (لا يتغيّر بنقل الموعد)
//   recurringEdited Boolean @default(false)
//   @@unique([recurringId, occurrenceDate])  @@index([recurringId, startAt])
```

قيود يدوية في الـ migration: `intervalWeeks BETWEEN 1 AND 4`، `startTime ~ '^([01][0-9]|2[0-3]):[0-5][0-9]$'`، `endDate IS NULL OR endDate >= startDate`. **لا يُمسّ** `bookings_no_overlap` ولا `btree_gist`.

### المنطق النقي (`modules/recurring/recurrence.ts` — بلا قاعدة بيانات)

- `occurrenceDates(series, from, to)`: `startDate + 7·N·k` ضمن `[max(from,startDate), min(to,endDate)]`.
- `serviceIndex(k, n)` و`occurrenceIndex(startDate, date, N)`.
- `planOccurrences({ series, services, hours, from, to, now, existingDates, busy })` ← `{ create: [{ date, k, serviceId, startAt, endAt }], issues: [{ date, k, reason }] }` حيث `reason ∈ CLOSED | OUTSIDE_HOURS | SERVICE_UNAVAILABLE | CONFLICT`؛ يضيف ما ينشئه إلى `busy` تدريجياً.
- `planSeriesChange(...)` للتعديل/الإيقاف (ومعاينتهما): يُرجع الحجوزات التي تُحذف والمواعيد التي تُنشأ والمشكلات وعدد المعدّل يدوياً الذي يبقى؛ ومعه `isRewritable` و`occurrenceStart`.

### الـ API (`modules/recurring/`) — `@Controller('recurring-bookings')`

| المسار                              | الصلاحية           | الوظيفة                                                              |
| ----------------------------------- | ------------------ | -------------------------------------------------------------------- |
| `GET /recurring-bookings`           | `recurring.read`   | السلاسل (الفعّالة أولاً) + الموعد القادم + عدد المشكلات              |
| `GET /recurring-bookings/:id`       | `recurring.read`   | القالب + المواعيد القادمة (حجوزات) + المشكلات                        |
| `POST /recurring-bookings/preview`  | `recurring.manage` | معاينة بلا كتابة: المواعيد والمشكلات، ومع `id` ما يتغيّر عند التعديل |
| `POST /recurring-bookings`          | `recurring.manage` | إنشاء السلسلة + توليد الأفق (معاملة واحدة)                           |
| `PATCH /recurring-bookings/:id`     | `recurring.manage` | تعديل القالب + إعادة كتابة المواعيد القادمة غير المعدّلة (D9)        |
| `POST /recurring-bookings/:id/stop` | `recurring.manage` | الإيقاف (D10)                                                        |

تعديلات على ما هو قائم: `Booking.recurringId`/`occurrenceDate` تظهر في استجابة الحجز؛ `BookingsService.update` يضع `recurringEdited`؛ `remove` يطبّق D8؛ `CustomersService.remove` و`ServicesService.remove` يحسبان الاستخدام الدوري؛ `AppConfig` + `env.validation` للمتغيّرين `RECURRING_HORIZON_DAYS` (افتراضي 56) و`RECURRING_SYNC_MINUTES` (افتراضي 360، `0` = معطّل).

### الواجهة

`/recurring` (قائمة) · `/recurring/new` و`/recurring/[id]/edit` (`RecurringForm`) · `/recurring/[id]` (تفاصيل). عنصر قائمة بصلاحية `recurring.read`. شارة «دوري» (أيقونة `repeat` + نص، لا لون وحده) في `BookingCard` و`BookingSheet`. المنتقي: `CustomerPicker` + أيام الأسبوع (الأيام العطلة معطّلة بنص) + «كل أسبوع / أسبوعين / 3 / 4» + `SlotPicker` للموعد الأول + قائمة خدمات مرتّبة (واحدة = ثابتة، أكثر = تناوب مع سطر «الأسبوع 1: … ← الأسبوع 2: …») + معاينة المواعيد القادمة والمشكلات قبل الحفظ.

## 4. المراحل

### المرحلة 1 — المحرّك النقي (بلا قاعدة بيانات ولا Prisma)

- `modules/recurring/recurrence.ts` + `recurrence.spec.ts` كما في §3. يستعمل `time.ts` و`schedule.ts` الموجودين (`zonedToUtc`, `shopWindow`, `overlaps`, `weekdayOf`, `addDays`, `diffDays`) ولا يكرّرهما.
- حالات الاختبار الإلزامية: أسبوع/أسبوعان/3/4 مع تحقق من **الطور** (أي أسبوع يقع فيه الموعد)؛ `endDate` شامل؛ `stoppedAt`؛ التناوب n=1 و2 و3 مع تكرار (أ،أ،ب)؛ استهلاك الدور عند وجود موعد موجود/مُلغى؛ يوم عطلة؛ خارج الدوام بداية ونهاية؛ دوام يتجاوز منتصف الليل (`closeTime ≤ openTime`)؛ خدمة غير متاحة؛ تداخل مع `busy`؛ `startAt ≤ now` يُتجاهل بصمت؛ `existingDates` تُتخطّى؛ حدّا الأفق؛ منطقة بتوقيت صيفي (مثل `America/New_York`) تثبت بقاء الساعة المحلية ثابتة، ودمشق (+3).
- **القبول:** `lint` و`typecheck` و`test` للـ API ينجحون؛ لا تغيير في أي ملف قائم.

### المرحلة 2 — المخطط والصلاحيات (بلا تطبيق على القاعدة)

- `schema.prisma` (§3) و`prisma generate`.
- **توليد SQL بلا اتصال بالقاعدة:** `prisma migrate diff --from-schema-datamodel <المخطط القديم من git> --to-schema-datamodel <الجديد> --script` ثم مراجعته يدوياً وإضافة القيود اليدوية (§3) و`IF NOT EXISTS`/`ON CONFLICT` حيث أمكن. **ممنوع `migrate dev`/`migrate reset`/`db push` على Supabase.**
- `prisma/permissions.ts`: `recurring.read` و`recurring.manage` في `PERMISSIONS` وفي `STAFF_PERMISSIONS` (D12) + migration بيانات idempotent في الملف نفسه (نمط `staff_restrictions`: `INSERT … ON CONFLICT` للصلاحيتين ثم ربطهما بالدورين).
- تحديث `seed.ts` إن لزم، و`permissions.matrix.spec.ts` (`STAFF_MUST_HAVE` حرفياً)، و`apps/web/tests/navigation.test.ts` لاحقاً في المرحلة 5.
- `docs/RECURRING_BOOKINGS_ROLLBACK.sql`: يحذف الجداول والأعمدة والقيود وروابط الصلاحيتين (يعمل بأمان قبل أي بيانات دورية).
- **إثبات الـ SQL دون إبقاء أثر:** سكربت يشغّله المستخدم أو بموافقته: `BEGIN; <migration.sql>; <تحققات>; ROLLBACK;` على Supabase (كما فُعل سابقاً)، يثبت: نجاح الأوامر، بقاء `bookings_no_overlap`، عدم تغيّر أعداد الصفوف، `ON CONFLICT DO NOTHING` يتخطّى فعلاً مخالفة القيد الفريد **وقيد EXCLUDE** (يحسم افتراض D7 قبل بناء المرحلة 3 عليه؛ إن لم يتخطَّ، المرحلة 3 تستعمل إدراجاً صفاً صفاً مع إعادة محاولة).
- **القبول:** الفحص الكامل ينجح؛ الـ migration مكتوبة ومراجعة ومثبتة بالتراجع؛ **لم تُطبَّق** على القاعدة.

### المرحلة 3 — خدمة التوليد والمزامنة (Prisma وهمي)

- `modules/recurring/recurring.service.ts` — دوال داخلية: `generate(seriesId|series, tx?)` (جلب `busy` مرة واحدة للأفق كاملاً، `planOccurrences`، `createMany skipDuplicates`، التحقق بإعادة الجلب)، `rewriteFuture(series)` للتعديل، `stop(series)`. الحجز المولَّد: لقطة الخدمة، `price = service.price`، `createdById = السلسلة.createdById`، `notes` من السلسلة، `occurrenceDate`.
